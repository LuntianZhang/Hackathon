# 从零理解 PanSense 的三维重建

> 面向第一次接触三维重建的读者。本文按当前仓库的 `main-gpu` 本机流程解释原理；文中的时间和效果均注明测试范围，不把局部测试当作完整产品性能。

## 先用一句话理解项目

PanSense 让用户上传餐盘照片或环绕视频。**单张照片**可以识别食物并记录餐食；**多视角视频或扫描照片**还能重建一个可旋转的三维餐盘。Food3D 是负责相机定位、三维建模、分割和语义融合的算法层，PanSense 是网页、任务管理和餐食记录层。

三维流程可以记为：**确定从哪里拍摄 → 训练场景外观 → 找出食物区域 → 把区域关联到三维模型**。

```text
环绕视频／扫描照片
    ↓ 抽帧、检查模糊与重复
有效照片
    ├─ COLMAP：相机位姿 + 稀疏三维点 ─→ Splatfacto：三维高斯模型 ─┐
    └─ SAM2：食物掩码 + CLIP：候选名称 ───────────────────────┤
                                                           ↓
                                        多视角融合：每个高斯的实例 ID
                                                           ↓
                                          三维查看、点击、体积与营养估算
```

应用的实际执行顺序是：抽帧 → COLMAP → 分割与跟踪 → Splatfacto 训练 → 导出 → 三维语义融合。上图把可以独立理解的“几何”和“语义”画成了两条线。[代码：视频任务](../src/pansense/jobs.py)

## 一、先认识五个词

| 词 | 通俗理解 | 在项目里的作用 |
|---|---|---|
| 帧 | 视频中的一张画面 | 相当于从不同角度拍的照片 |
| 相机位姿 | 拍摄时相机在三维空间的位置和朝向 | 告诉训练程序“这张照片是从哪里看到的” |
| 稀疏点云 | 不同照片中能对应起来的少量三维特征点 | 给高斯模型提供初始位置；它不是完整物体表面 |
| 掩码 | 与照片同尺寸的区域图，标出哪些像素属于某个物体 | 给食物实例提供二维证据 |
| 三维高斯 | 一个带位置、形状、颜色和透明度的三维“小椭球” | 很多高斯一起近似场景外观，可从新视角渲染 |

“实例”指**某一个具体物体**。同一餐盘里的两根香蕉应有两个不同的实例 ID，即使它们的类别都叫香蕉。名称可以改，实例 ID 不因此改变。

## 二、输入怎样变成可用于训练的照片

视频先由 FFmpeg 选取画面，程序检查清晰度和与前一张有效画面的差异，排除模糊或近乎重复的画面。每张候选帧及其时间戳、是否通过筛选，都保存在 `frame_manifest.json`。因此“原视频有多少帧”和“最终用于重建的有效帧数”不是一回事。[代码：抽帧与筛选](../src/food3d/data/frames.py)

拍摄时要让餐盘和食物保持静止，围绕它改变相机视角；相邻画面需要有足够重叠。固定镜头和变焦也很重要，否则相机参数会变化。只拍一张照片，无法仅凭这张照片可靠恢复被遮挡的背面。

当前应用的 Linux 配置对视频最多保留 120 张候选画面，并要求 COLMAP 最终至少注册 20 张；这些是流程门槛，不是“达到门槛就一定有好模型”的保证。[配置：抽帧与 COLMAP](../configs/fruit2_video_linux.yaml)

## 三、COLMAP：先解决“相机在哪里”

假设同一个纸条角点出现在多张照片中：如果知道它在每张照片的像素位置，就能反过来推测相机的相对位置，并估计这个角点的三维位置。COLMAP 将这件事规模化处理：

1. **提取特征**：在每张图里找便于重复识别的局部纹理点，当前使用 SIFT。
2. **跨图匹配**：判断两张图里哪些点可能是同一个真实位置，并做几何检验。
3. **增量建图**：逐步加入照片，估计相机位姿与稀疏三维点，再联合优化它们，让三维点投影回照片时尽量对齐原特征。
4. **去畸变与导出**：生成用于后续训练的图片、相机参数 `transforms.json` 和初始点云 `sparse_points.ply`。

**COLMAP 本身不认识“苹果”或“香蕉”，也不会输出完整三维餐盘。** 如果视角缺少重叠、画面模糊、物体在拍摄时移动，位姿求解就可能失败；后面的三维训练不能自动修复错误位姿。[代码：COLMAP](../src/food3d/data/colmap.py)、[代码：相机数据导出](../src/food3d/data/cameras.py)

### 本机 CPU 和 GPU 怎么分工

一份本地 Linux 配置让 **GPU 提取 SIFT 特征、CPU 做引导匹配**。这不是说匹配不能用 GPU，而是那组测试图片上 CPU 更快。COLMAP 的增量建图和相机优化仍由 CPU 执行。`matching_use_gpu: false` 只影响匹配，不会关闭 Splatfacto 的 GPU 训练。其他机器应分别测量与检查驱动支持情况。

## 四、Splatfacto：项目里说的“训练”是什么

这里的训练是**为这一次上传的场景优化一个专属三维模型**。它不等于重新训练一个通用食物识别网络。SAM2、CLIP 使用已有权重做推理；新的视频通常要重新求位姿并训练新的高斯集合。

这里几个常见术语可以先翻译成日常语言：**渲染**是让电脑模拟“从指定位置拍一张照片”；**损失**是预测照片与真实照片的差距；**反向传播**是计算每个参数怎样改变才能缩小差距；**SSIM**侧重比较图像局部结构是否相似；**球谐系数**是一组让颜色随观察方向变化的参数。

一个高斯至少有这些可调参数：中心位置、三个方向的大小、朝向、透明度，以及颜色。颜色可以用球谐系数表示，因此从不同方向看时可以呈现不同外观。COLMAP 的稀疏点为高斯提供初始位置和颜色。[代码：输入点云](../src/food3d/data/cameras.py)、[代码：训练入口](../src/food3d/reconstruction/train_worker.py)

**一次训练迭代**可以想成下面的循环：

1. 取一个已知相机位置及其真实照片。
2. 把当前高斯模型从这个相机位置投影并渲染，得到一张“预测照片”。同一像素上的高斯按前后顺序，以颜色和透明度合成。
3. 比较预测照片和真实照片。如果某处颜色或结构不对，就产生误差。
4. PyTorch 通过反向传播计算每个高斯参数应该怎么改，优化器更新参数。
5. 重复许多次；训练中还会增加需要更多细节的高斯，并删除贡献小或异常的高斯。

仓库环境记录中的 Nerfstudio Splatfacto 版本将主要训练误差写成：

```text
损失 = 0.8 × 平均像素颜色差 + 0.2 × (1 - 图像结构相似度 SSIM)
```

这是一种**用照片监督三维外观**的方法，不需要给每个高斯预先标注正确三维位置。LPIPS 在该版本中主要用于图像评估，不能把它说成上述主要训练损失。不同安装版本应以实际代码为准。[版本记录](../environments/README.md)

一份本地配置训练 **2000 步**，已提交的应用配置为 **3000 步**；两者都不是对所有餐盘有效的固定要求。训练使用约 90% 的输入视角作 Nerfstudio 训练划分，白色背景，并关闭训练时的相机位姿优化。当前实现先经过 500 步预热，之后约每 100 步进行一次高斯增减检查。训练完成会生成 checkpoint，再导出 `gaussians.npz`、`gaussians.ply` 与匹配的相机数据。[配置：应用步数](../configs/pansense.yaml)、[代码：训练与导出](../src/food3d/reconstruction/export.py)

### 为什么 100 步测试不能代表最终效果

开发时做过一次 **12 视角、约 2800 个初始高斯、100 步**的模拟场景短训练，能够生成 checkpoint 并导出模型。这只验证 CUDA、Nerfstudio、gsplat 和导出链路可以跑通。100 步还未到上述 500 步增减高斯的阶段；真实餐盘的照片数、纹理和高斯数量也不同，因此不能用那次几秒的稳定单步耗时推算完整项目只需几秒。

## 五、SAM2 和 CLIP：找物体，再确定名称

三维模型首先学习的是**外观**，不知道某团高斯属于哪种食物。SAM2 给出食物掩码，并把同一物体的掩码传播到其他视角；自动模式可以用 CLIP 比较候选名称，多视角大模型模式则由视觉 Agent 命名。用户也可以给名称、点或框来辅助识别。定位板背景排除会先为相机匹配和训练图准备前景区域；正式实例分割按所选识别方式运行。[代码：多视角分割](../src/food3d/segmentation/sam2.py)、[背景排除过程](PanSense_技术文档.md#32-可选的背景排除)

**CLIP 分数不是识别正确率。** 相似食物、遮挡、反光或非食物画面都可能导致错误名称；界面要求用户核对。即使名字错了，只要掩码和实例身份可靠，也可以改名而保留原来的三维实例 ID。

## 六、怎样把二维掩码贴到三维模型上

不能简单把某一张照片上的红色区域当作整件三维物体：从另一个方向看，遮挡关系会变化。项目按每个已知相机视角渲染高斯，检查**某个高斯对某个像素实际贡献了多少颜色／透明度**，再结合像素掩码、深度一致性和边缘可靠性，对同一高斯累积多个视角的证据。当前融合至少需要 3 个支持视角；证据不足则保持“未知”。[代码：融合](../src/food3d/fusion/pipeline.py)、[代码：可见贡献](../src/food3d/fusion/visibility.py)

这样得到的不是“整张图片对应一个食物标签”，而是**每个固定高斯对应一个实例 ID**。三维渲染和点击读取这个结果，所以旋转视角后，物体的身份仍可保持一致。若重新训练导致高斯增加、删除或排序变化，语义绑定必须重新融合。[代码：三维渲染](../src/food3d/viewer/renderer.py)

## 七、体积和营养从哪里来

COLMAP 和高斯训练得到的是一个**相对尺度**的三维世界；没有实测参照物，不能直接说某个物体是多少毫升。项目用已知尺寸的定位板估计厘米与模型单位的换算关系。体积方面，从置信度足够的同一实例高斯中心取样，计算三维**凸包包围体积**，再按尺度的三次方换成 mL。之后可以用 `体积 × 密度 = 估计重量`，按食物营养数据换算这一份的大致营养。[代码：体积](../src/food3d/volume.py)、[代码：密度与营养](../src/pansense/quantities.py)

凸包会填满香蕉的弯曲空隙；没拍到的背面、误分割、尺度误差也会影响结果。因此这里应说**粗略估算体积、重量和营养**，不能说是称重或经过实物体积真值验证。

## 八、部署时怎样理解计算分工

抽帧和图像质量筛选主要处理普通图片；COLMAP 的特征提取与匹配是否用 GPU 由安装版本和场景配置决定，增量建图还包含大量 CPU 工作。SAM 2、Splatfacto、高斯渲染及语义融合则需要能够运行相应模型的 GPU 环境。某一步使用了 GPU，不代表整条任务都只在 GPU 上运行。[部署与检查步骤](PanSense_技术文档.md#7-部署与复现计算平台环境和路径)。

一段视频的总耗时还包含抽帧、模型识别、相机重建、三维训练、导出、语义融合和等待队列。输入照片数、画面尺寸、可见物体、训练步数及计算设备都会改变时间，不能拿另一台机器的一次计时当作本机预计完成时间。要比较优化，应使用相同输入、相同质量目标和独立输出目录，并核对模型是否仍通过相机、点击和体积检查。[实验结果的读法](PanSense_技术文档.md#8-实验结果应该怎样读)。

## 九、自己运行与观察什么

在工程根目录按[部署章节](PanSense_技术文档.md#7-部署与复现计算平台环境和路径)准备本机配置并启动网页。先检查两套 Python 环境、GPU 和必需工具，再用自己的素材创建新任务。

浏览器打开 `http://127.0.0.1:8000`。先用照片体验识别与人工纠错；要体验三维，使用围绕静止餐盘拍摄、视角连续且清晰的视频。可以从以下几个产物观察各阶段：

| 文件 | 用来检查什么 |
|---|---|
| `scene/frame_manifest.json` | 采样了多少帧、为什么有帧被丢弃 |
| `scene/colmap_selection.json`、`scene/validation.json` | 相机实际注册了多少张、是否生成场景 |
| `scene/transforms.json`、`scene/sparse_points.ply` | 训练所用相机与初始点云 |
| `training/training.log`、`*.ckpt` | 训练是否完成、步数与日志 |
| `bundle/gaussians.ply`、`bundle/model.json` | 最终高斯与模型元数据 |
| `bundle/semantics/fusion.json` | 哪些视角参与语义投票 |
| `evaluation/report.json` | 相对 SAM2 掩码的多视角一致性与点击检查 |

应用给每次任务建立单独目录，具体路径以实际任务日志为准。单看训练成功、相机注册数量高，仍不足以判断餐盘的背面几何或食物名称正确。

## 十、适合在 pre 中说的 90 秒版本

> 我们的系统先从环绕视频里筛选有效画面，再用 COLMAP 恢复每张画面的相机位置和少量三维点。然后用 Splatfacto 针对这一次餐盘训练三维高斯模型：从已知相机位置渲染预测图，与真实照片比较，并不断调整高斯的位置、颜色和透明度。另一条流程用 SAM2 找到食物区域、跨视角跟踪，再把二维实例对应到三维高斯，支持旋转查看和点击。若定位板提供可靠尺度，再粗略估计体积。运行时间随显卡、输入视角和配置变化；真实体积精度仍需实物测量验证。

### 常见追问

- **为什么不直接用一张照片生成三维？** 单张照片缺少背面和遮挡信息；项目依赖多视角的共同约束。
- **COLMAP 与 Splatfacto 分别做什么？** COLMAP 给相机位姿和稀疏点；Splatfacto 优化可渲染的三维外观。
- **每次上传都会重新训练 SAM2/CLIP 吗？** 不会。它们使用已有权重推理；重新训练的是该场景的高斯参数。
- **高斯模型等于精确几何或真实体积吗？** 不等于。它首先是外观表示；体积来自可靠高斯中心的凸包近似，并需要真实尺度标定。
- **100 步短训练为什么能出图，却不能当成最终模型？** 它只证明链路能跑，尚未到默认 500 步之后的高斯增减阶段，视角与场景也远小于实际任务。

如果要做五页展示，可以按 **问题与输入 → 相机定位 → 高斯训练循环 → 食物语义与交互 → 实测证据和局限** 排列。讲性能时明确测试设备、照片数量、分辨率、是否包含引导匹配，以及计时覆盖了哪一步。
