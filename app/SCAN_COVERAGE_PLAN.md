# 摄像头环绕扫描与拍摄角度覆盖图：功能规划

状态：**仅规划，尚未实现**。更新日期：2026-10-16。

本文与配套 SVG 都是设计资料，不新增运行入口、摄像头调用或后端接口。

## 已确认的部署方式与设备分工

本次采用“手机浏览器采集，电脑运行与处理”。手机通过 HTTPS 访问电脑提供的轻量拍摄页，授权后调用手机后置摄像头；不安装手机 App，不将现有完整软件或模型移植到手机。

- **手机**：摄像头取景、开始 / 暂停 / 结束、采集并上传照片或视频帧、显示电脑返回的角度覆盖与补拍提示。角度图仍显示在手机取景画面旁边，竖屏时放在下方。
- **电脑**：提供 HTTPS 拍摄入口，创建扫描会话、接收与保存图像、检查清晰度、估计拍摄位置与覆盖方向，执行后续分割和三维重建。电脑主界面可同步查看采集进度。
- **连接**：首版使用手机与电脑在同一局域网的方式，电脑显示二维码供手机打开。手机访问的是电脑的局域网地址或域名，不能使用手机自身的 `localhost`。具体地址和证书配置留待实施时确认。
- **权限与页面**：手机浏览器需要可信的 HTTPS 安全上下文及用户摄像头授权。拍摄页和上传、反馈通道使用同一 HTTPS 入口；首版只申请视频，不申请麦克风。
- **反馈**：手机上传画面，电脑返回角度状态与下一步提示。摄像头连通与图像上传不代表角度定位已解决；实时角度识别路线需要独立验证，无法可靠定位时明确显示“角度待确认”。

```text
手机后置摄像头 → HTTPS 上传图像 → 电脑：保存、质量检查、角度估计
手机取景页 / 角度图 ← HTTPS 状态反馈 ← 电脑：覆盖格与补拍建议
结束扫描 → 电脑复核照片 → 现有分割与重建流程
```

此确认只调整功能规划，不修改应用、开放网络端口、配置证书或启动摄像头。

## 1. 用户会看到什么

打开“环绕扫描”，屏幕显示实时后置摄像头画面；旁边是一张围绕食物的**拍摄方向地图**。手机竖屏时，覆盖图放在画面下方，保持可见；横屏和桌面并排展示。

地图用两层分段圆环表达不同高度：较低视角一圈、较高俯视一圈。中心是餐盘或食物图标；起点方向作为相对 0°，无需知道地理北方。当前相机位置以蓝色箭头表示，推荐补拍区域以描边闪示。

| 图形状态 | 对用户的含义 | 能否计入已覆盖 |
|---|---|---|
| 灰色空段 | 这个方向还没有合格照片 | 否 |
| 黄色虚线段 | 已有候选照片，保存或位姿确认未完成 | 否 |
| 绿色带勾段 | 该方向有已保存且通过图像与位姿检查的照片 | 是 |
| 红色带叹号段 | 曾拍过，但模糊、缺少重叠或定位失效，需要补拍 | 否 |
| 蓝色箭头 | 当前估计位置；与格子状态分开显示 | 不计数 |

没有可靠角度的照片放在“待定位”缩略图区，不凭手机朝向硬塞进某个方向格。颜色同时搭配勾号、虚线、叹号和文字，避免只靠颜色区分。

点某个方向，展开该方向的照片缩略图、质量原因和“前往补拍”提示。底部显示：已覆盖方向数、合格照片数、缺失方向，以及“暂停 / 继续”“结束并检查”操作。示意图见 [配套 SVG](scan_coverage_mockup.svg)，其中数字是设计示例。

## 2. 操作流程

1. **准备**：选择整盘或单个食物；可输入食物清单。提示物体静止、保持光照、围绕移动，避免转动餐盘。
2. **建立中心**：将食物放入取景框，确认扫描中心。必须获得与相机位姿同一坐标系的中心点，再开始计算环绕角度。
3. **建立定位**：检查摄像头、位置追踪和画面清晰度。初次需要用户点击允许摄像头；姿态权限按设备能力处理。
4. **第一圈**：在较低视角缓慢绕行，自动选取合格关键帧。覆盖格随成功采集更新，不按倒计时或照片张数自动变绿。
5. **第二圈**：抬高手机，再补拍较高俯视的一圈；界面提示“继续向右移动”“抬高一点”“请停稳”“保持食物在画面内”。
6. **检查**：结束后运行 COLMAP 几何复核，显示已注册相机与最终方向缺口。补拍仍属于同一会话，接入既有场景后重算覆盖图。
7. **重建**：用户确认后，把已选照片送进现有 COLMAP → Splatfacto → 分割 → 三维语义融合流程。

首版以整盘的采集方向为单位，不宣称绿格代表每个食物的所有表面都已看到。多食物相互遮挡时，后续再增加逐实例覆盖。

## 3. 技术可行性与推荐路线

界面和自动采帧可直接扩展现有 PWA。难点是**相机相对食物的位置**：设备方向不等于环绕位置，人在原地旋转手机不能算绕食物拍了一圈。设备方向事件提供旋转信息，不能单独作为位置依据。[W3C Device Orientation](https://www.w3.org/TR/orientation-event/)

建议将“位姿提供器”单独设计，先验证准确性再决定正式产品的采集方式：

| 路线 | 可提供的反馈 | 适用性与代价 |
|---|---|---|
| PWA + 方向传感器 + 拍后 COLMAP | 扫描时给移动提示；几何处理后确认覆盖 | 无标记兼容模式；扫描中不能承诺精确的实时方向覆盖 |
| PWA + 已知布局的 ArUco 标记板 + PnP | 标记可见且内参有效时，实时估计位置并更新方向图 | **首个准确角度 POC 推荐**；需在餐盘周围放置标记板，并验证遮挡和斜视条件 |
| 浏览器可用的 6DoF 追踪 + 场景锚点 | 连续位置与姿态，可支撑无标记实时覆盖 | 后续可行性研究；需验证目标浏览器能力及相机帧访问，本次不做原生 ARCore / ARKit 应用适配 |

OpenCV 提供 ArUco 检测及基于标记角点的位姿估计流程，可复用而不重写定位算法。标记板应有多个已知相对布局的标记，使绕行时仍能看到一部分；不假设一张侧放二维码能覆盖整圈。准确位姿依赖相机内参、标记尺寸及图像对应关系，不能将“检测到四个角”直接视为准确定位。[OpenCV ArUco 文档](https://docs.opencv.org/4.x/d5/dae/tutorial_aruco_detection.html)

WebXR 的位置与姿态在规范中有明确表示，但位置也可能被模拟；不能只检查接口存在就认为追踪可靠。还需验证保存的照片与追踪位姿对应，不能假定 XR 背景画面可直接作为训练照片读取。[W3C WebXR](https://www.w3.org/TR/webxr/)

**建议顺序**：先验证“手机 HTTPS 取景与上传 → 电脑接收与保存 → 手机显示反馈”，再用标记板与电脑端图像处理验证“实际绕行 → 正确方向格 → 合格照片 → COLMAP 复核”，随后评估去标记方案。暂时没有可靠位置的设备保留采集能力，明确显示“方向待确认”。不为了完成动画而将陀螺仪数据当成精确位置。

## 4. 角度地图与合格照片规则

### 4.1 空间定义

- 初始地图为水平方位 12 段 × 两个高度带，共 24 个目标格。每段 30°，左右绕行均可，0° / 360° 连续。
- 初始高度带建议为相对水平面 15°–40°、40°–70°，以 30°、55°为引导位置；70°以上的顶部照作为额外建议，不计入首版 24 格分母。
- 以上分段和数量是待实测的产品初值，不是已验证的重建标准。目标先尝试约 48–72 张合格关键帧，现有视频流程的最低注册帧数仍需独立满足。
- 相机与食物中心必须使用统一坐标、相同原点及上方向；相机轴和世界轴不同，适配器需转换到项目约定。首版将桌面足迹中心作为扫描锚点，定义高度带也基于该锚点，并记录这一近似。

给定食物中心 `c`、相机中心 `p`、桌面法向 `up`、起始水平单位方向 `forward`，定义 `right = up × forward`：

```text
v = p - c
h = v - dot(v, up) * up
azimuth = atan2(dot(h, right), dot(h, forward)) mod 360°
elevation = atan2(dot(v, up), norm(h))
```

对处于中心上方、水平距离过小的相机单独记为顶部视角，避免方位抖动。边界采用滞回和位置平滑；位姿重定位时暂停更新，而不是把方向图突然转一圈。

标记板路线中，先用板建立桌面坐标，再将首帧用户确认的食物中心射线与桌面相交得到锚点；这要求可用的相机内参和外参。无平面或无可靠内参时，不声称准确定位。6DoF 路线则需通过可用的平面 / 命中测试建立同坐标锚点，不能用屏幕坐标直接代替三维中心。

### 4.2 采帧与质量检查

一个方向格变绿需同时满足：

- 至少有两张已成功保存、位姿可靠的不同视点照片；同一位置重复拍十张不增加覆盖。格内两帧的方位差可先试 5°–10°，再按距离、画面重叠和特征匹配校准。
- 对焦与清晰度合格、曝光可用、目标区域没有明显裁切，并与相邻关键帧有足够视觉重叠。沿用现有清晰度指标作为起点，但阈值要按视频分辨率重新标定。
- 关键帧间存在有效平移 / 视差；禁止只根据画面差异或陀螺仪角度判定“新角度”。
- 该格中的有效帧未被用户删除或复核淘汰。删除最后的合格支持帧后，格子应退回待补拍，而不是永久变绿。

COLMAP 官方建议高视觉重叠并让对象出现在多个视图中；分段计数不能替代这一要求。[COLMAP 拍摄指南](https://colmap.github.io/tutorial.html)

自动选择帧时优先补缺失方向，但仍保留连接相邻方向的过渡帧。实时预览保持独立，不在每个预览帧运行 SAM 2、CLIP 或 Splatfacto。初步可用 1–3 fps 的低分辨率分析流，保存清晰原图；实际速率由设备和后端延迟实测决定。

采集阶段的绿色表示“该方向已有通过在线检查的照片”；结束后的复核将其标为“几何已确认”或退回补拍。进度文案使用“采集覆盖”“几何确认覆盖”，不写“模型完成度 100%”。角度齐全也不保证反光、遮挡或低纹理表面重建成功。

## 5. 模块与数据契约（拟定，不新增文件实现）

```text
PWA 摄像头预览
  → 采帧器 + 时间戳 / 相机参数
  → 位姿提供器（标记板 / 成熟 6DoF / 待定位降级）
  → 食物锚点 + 图像质量 / 视差 / 重叠检查
  → 关键帧保存确认 → 角度覆盖汇总 → 圆环图 + 缩略图
  → 结束扫描 → COLMAP 复核 → 缺口补拍 / 现有重建流水线
```

建议未来拆分 `capture`、`pose_provider`、`coverage` 三个模块；复用已有 `CameraFrame` 坐标契约、照片导入、COLMAP 和 GPU 队列。覆盖算法及模拟数据测试可先在 CPU 进行。

每个扫描会话拟保存：

| 数据 | 关键字段 |
|---|---|
| 会话 | `scan_id`、`revision`、状态、目标类型、食物清单、坐标系 ID、中心锚点及版本、目标格定义 |
| 关键帧 | 稳定 `frame_id`、采集时间戳、图像尺寸 / 哈希、对应内参、位姿来源、追踪状态、位姿时间戳、质量结果、保存确认 |
| 角度证据 | 方位 / 高度、`sector_id`（可为空）、支持帧列表、在线 / 几何复核状态及拒绝原因 |
| 最终结果 | COLMAP 注册帧、统一坐标后的相机中心、复核覆盖图、缺失方向、后续场景路径 |

预览图、保存图和传感器数据必须时间对齐。图像缩放、裁切、旋转、切换镜头或变焦后，需匹配更新内参；不将后端收到时间当成手机曝光时间。位姿事件应带递增序号，客户端丢弃过期反馈。

拟定接口为“创建会话 / 上传关键帧 / 接收状态事件 / 暂停 / 结束复核 / 继续补拍 / 开始重建”。上传需幂等，重复传输同一 `frame_id` 不增加覆盖。保存或上传失败不能先标绿；后台切换时先暂停，恢复后重新检查锚点和追踪。

COLMAP 复核使用重建后的坐标重新计算覆盖，不能与在线位姿直接拼接。需通过公共已注册帧做坐标对齐、恢复桌面上方向及中心锚点；若无法可靠对齐，展示新的复核地图，不做虚假的逐格对应。补拍帧需注册进同一场景，再重新融合地图。

## 6. 现有项目需要调整的地方

- `app/web/app.js`：现有移动端“打开相机”直接调系统拍照输入，不是连续取景。未来新增独立环绕扫描入口，使用嵌入式预览；保留已有单张拍照方式。
- `src/pansense/api.py`：目前只允许本机主机名；手机访问桌面后端的部署、允许的主机及同源 HTTPS 入口需专门配置。手机上的 `127.0.0.1` 指向手机自身，不能沿用桌面地址。
- 摄像头接口要求安全上下文，物理手机访问局域网服务需规划可信 HTTPS；权限拒绝时保留相册导入。具体浏览器能力要在目标 iOS / Android 设备上验证，不按操作系统名称直接假定支持。[Media Capture 规范](https://www.w3.org/TR/mediacapture-streams/)
- `src/pansense/jobs.py`：新增扫描照片会话的入口，避免把实时反馈排在完整 Splatfacto 训练任务后。定位 / 图像检查走轻量任务；训练仍进入已有串行 GPU 队列。
- 图像识别在初始化 / 用户要求时运行，沿用三种辅助方式。首版不要求每一帧完成食物分类或三维语义渲染。

## 7. 开发阶段与验收

| 阶段 | 工作 | 通过条件 |
|---|---|---|
| A：定位可行性小实验 | 目标手机 HTTPS 连通；相机内参来源；标记板 / 6DoF 能力与照片同步 | 能区分原地旋转和真实绕行；中心锚点不随人移动 |
| B：采集与地图 | 预览、两层方向图、质量检查、自动关键帧、保存确认 | 原地拍摄不填满圆环；模糊帧不计覆盖；可点格子查看对应照片 |
| C：复核与补拍 | COLMAP 注册、坐标对齐、缺口提示、同会话追加 | 缺少后侧 / 高角度时能指出；补拍后缺口实际减少 |
| D：接入重建 | 使用合格关键帧运行现有流水线 | 在真实苹果、香蕉、面包场景完成重建与语义点击，并记录失败场景 |

专门验收：原地旋转、重复静止拍照、真实绕一圈、只拍低视角、位姿丢失、标记遮挡、模糊 / 反光、目标移动、上传失败、删除照片、切换横竖屏、浏览器进入后台。无位姿或位姿不可靠时，必须显示待确认。

比较覆盖结果与 COLMAP 复核地图，记录格子误报率、漏报率、角度偏差、注册帧比例及反馈延迟。初步将“原地旋转不新增覆盖”和“保存失败不新增覆盖”设为硬性要求；精度、完成门槛及性能指标在阶段 A 根据目标设备确定，不提前承诺。

首版边界：静止桌面场景、整盘方向覆盖；不要求扫描底部、不保证逐食物无盲区、不支持转盘与相机同时移动、不在扫描时训练 3DGS。本文未实施上述任何运行功能。
